## Problem

HARN-OPT-1 shipped the run ledger and the delivery optimiser. Both work: the
optimiser's first live runs produced cited, actionable proposals against the
delivery repos (consolidate two overlapping AI-review workflows costing ~650s
of compute per PR; instrument CI per-stage timing before cutting anything).

Those same runs exposed three defects that four rounds of fixture-based review
did not, because fixtures agreed with the code's assumptions and real data did
not. Two corrupt the telemetry the optimiser depends on; one blocks the
recurring cadence §9 asks for. All three were found **by the optimiser
itself**, which is the improvement loop working as designed.

**1. Plan identity is not normalised.** One plan was scattered across four
`byPlan` buckets in a 9-record ledger.

> **CORRECTED.** The headline case I named — an absolute path under the repo
> root — **is already fixed**: `lens-simplicity` ran the shipped writer and
> `redactPaths` relativises it. The live absolute-path line predates that fix.
> Also, the "stray `specs/x.md`" is **not a defect symptom at all**: it is a
> hand-written test record (`run_id:"r1"`) I injected during earlier probing,
> polluting my own evidence.
> The **real uncovered case**, found by `lens-data` and `lens-architecture`
> with real `git worktree add` fixtures: a worktree-authored absolute spec
> writes both a redacted `spec` **and** `repo:"<worktree-dirname>"`, so two
> different plans merge into one bucket *and* one repo splits into two
> identities. Worktrees are this harness's normal execution mode, so this is
> more pervasive than the case I originally named. A second uncovered case
> (`AC-SEC-1`): a relative path with `..` resolving outside the root is
> written **verbatim**, leaking e.g. `../../../home/<user>/.ssh/config`.
> Covered by AC-DATA-1, AC-DATA-2, AC-ARCH-3, AC-OPS-5, AC-SEC-1.

**2. Start/terminal events are unpaired.**

> **CORRECTED, twice over.** The count and the cause were both wrong.
> `lens-operability` grouped the live ledger by run_id and measured
> `{paired:1, startOnly:4, termOnly:2}` — **two orphans are terminal-only**
> (a failed *start* write), a different defect with a different fix. The
> aggregator collapses both orphan classes into one counter, so a fix to the
> start-only half alone would move the number 6 → 2 and **read as progress
> while a second defect remains**.
> The cause is not "the terminal write is not reached on some return path":
> `lens-qa` **executed** it — a stubbed agent throwing inside `run()`
> produces exactly one ledger write and the error propagates out. The cause
> is **an exception escaping `run()`** (no `try/finally` at tdd-task.js:283,
> review-cycle.js:409, plan-cycle.js:240). Every `return` path is already
> funnelled and `test/tdd-task.test.js:62` covers them, green. An implementer
> following my original wording would have re-verified the correct half.
> Covered by AC-QA-8, AC-QA-9, AC-OPS-1, AC-OPS-2, AC-DATA-9, AC-DATA-10.

**3. The optimiser cannot run without a local checkout.** It resolves repo
identity and git history from a working tree on disk. A cloud routine has no
such checkout, and the ledger is deliberately gitignored and local, so
cloud-side ledger analysis is impossible by design. The weekly cadence
currently runs as a local launchd job (`com.local.optimise-cycle-weekly`,
Mondays 07:41).

> **CORRECTED — my justification for building PR 3 was factually wrong.** I
> claimed the launchd job "only fires when this machine is awake".
> `lens-simplicity` checked `man 5 launchd.plist`: launchd **coalesces missed
> `StartCalendarInterval` firings and runs them on wake**, unlike cron. So the
> local schedule is materially more reliable than I told the operator, and the
> strongest stated reason to build PR 3 evaporates.
> The real weakness of the local job is different and unaddressed: **silent
> failure.** `launchctl list` reports the last exit status (currently -15 from
> the deliberate wiring test) and nothing surfaces it to anyone.
> Consequently PR 3 is **sequenced last and gated** on AC-PROD-11: it is built
> only if a measured miss rate justifies it. Its 20 criteria are marked
> *(PR 3 only)* and bind only if that gate opens.

Left unfixed, (1) and (2) mean the ledger accumulates data that looks
complete and is not — the exact failure the ledger was built to prevent, and
the reason to fix them **now**, while the ledger is nearly empty, rather than
after months of unusable history.

## Shape of the change

Three deliverables, conductable as one plan. (1) and (2) are independent of
(3) and can run in parallel.

**PR 1 — plan identity normalisation.** Canonicalise plan identity to a
single key (repo + repo-relative resolved spec path) at the point the ledger
writer records it, so one plan yields one bucket. Covers: absolute vs relative
paths, missing spec (`unspecified` must remain distinguishable from a real
plan, not merge into one), and symlinked or `..`-containing paths. Existing
ledger lines are not rewritten (append-only, AC-DATA-2); the optimiser's
reader normalises historical keys on read so the small existing corpus stays
usable.

**PR 2 — start/terminal pairing.** Wrap the workflow body in `try/finally`
(or equivalent) at tdd-task.js:283, review-cycle.js:409 and plan-cycle.js:240
so an **exception escaping `run()`** still writes a terminal record — this,
not an unfunnelled `return`, is the measured cause. Separately handle the
**terminal-only** orphans (a failed *start* write). The aggregator must count
and name the two orphan classes **separately**, so fixing one cannot read as
progress while the other persists. The abort case must stay distinguishable
from a genuine completion.

**PR 3 — slug-only / CI-only mode. GATED (AC-PROD-11), sequenced last.**
A mode that analyses CI and remote git history from a repo slug alone
(`owner/name`), with no local checkout, labelling ledger-derived sections
unavailable-by-design rather than empty. Built **only if** the gate opens:
the launchd job's measured miss rate justifies it. Since launchd coalesces
missed firings on wake, the expected miss rate may be near zero, in which
case the cheaper fix is surfacing the local job's silent failures instead.

**Then:** if PR 3 is built, stand up cloud routines and decide whether the
local launchd job stays or is retired. If PR 3 is gated out, add failure
surfacing to the local job instead. Not pre-judged here.

**Deployment gap that applies to PR 1 and PR 2 (AC-OPS-4).** The installed
mirror at `~/.claude/workflows/lib/` is what actually executes for the
delivery repos, not the repo copy. Both PRs can land green with live
telemetry still broken. The mirror must be re-synced and verified as part of
each PR's definition of done — this is the §11 "correct in source, absent
from the build" shape, and it is now the harness's own deployment surface.

## Not in scope

- **Making the ledger cloud-reachable** (syncing it to a private repo, or a
  hosted store). That reopens the AC-SEC-1 privacy decision and deserves its
  own spec. Until then, ledger analysis is local-only by design, and the
  slug-only mode must say so rather than imply the data is merely absent.
- **Rewriting existing ledger lines.** Append-only stands; normalisation
  happens on read.
- **Acting on the optimiser's own T4 proposals** (consolidating the duplicate
  AI-review workflows, instrumenting CI timing). Those are changes to the
  delivery repos, tracked separately — this spec only makes the measurement
  trustworthy.
- **Per-PR wall-clock attribution.** The ledger has no PR-number field and
  groups by spec path; adding one is a larger telemetry change and no
  proposal currently depends on it.

## Risks

- **Normalisation merges things that are genuinely distinct.** Collapsing
  `unspecified` into a real plan, or two different specs with the same
  basename, would hide work rather than reveal it. Mitigation: an AC
  requiring distinct inputs to stay distinct, tested with a colliding-basename
  fixture.
- **The pairing fix hides the failure instead of fixing it.** Emitting a
  terminal record unconditionally (e.g. in a wrapper that always runs) would
  make unpaired starts disappear without the underlying run actually
  completing. Mitigation: the aborted/unterminated outcome must remain
  distinguishable from a genuine completion, per AC-DATA-5.
- **Slug-only mode silently degrades to a half-report.** If it renders empty
  ledger sections rather than explicitly-unavailable ones, a weekly cloud
  report will read as "nothing to improve". Mitigation: an AC requiring the
  distinction, mirroring the existing uninstrumented-vs-no-activity rule
  (AC-OPS-11).
